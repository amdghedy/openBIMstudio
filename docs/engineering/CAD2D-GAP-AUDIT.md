# 2D CAD engine — AutoCAD gap audit and milestone roadmap

Status labels: **Implemented** (works, tested), **Limited** (works with a documented loss), **Experimental**, **Planned**.
Every row cites the source that was inspected. Nothing here was checked against a desktop AutoCAD install
(none is available in CI); interoperability claims rest on ezdxf and the project's own DWG engine only.

## 1. Architecture as found

- **One drawing model**: `DxfDocument` / `DxfEntity` (`src/modules/drawings/dxf-types.ts`). The entity union has only
  LINE, CIRCLE, ARC, LWPOLYLINE, TEXT (also carries MTEXT), POINT, RAY, XLINE. Hatches, fills, wipeouts and
  dimensions are encoded as flags/metadata on those types, not as entities of their own.
- **Two readers feed it**: `dxf-reader.ts` (DXF) and `acad-engine.ts` (DWG through the acadrust WASM engine), plus
  `dwg-convert.ts` for the LibreDWG fallback. All three *flatten* on read.
- **One command table**: `CAD_COMMANDS` and `executeDrawingCommand` in `src/features/cad-viewer.ts` (13.5k lines).
  New work must extend it, not create a second engine.
- **Writer**: `dxf-writer.ts` (R2010 ASCII); DWG output goes through the same document.

## 2. Confirmed gaps (flattening at read time)

| Area | Finding | Evidence |
|---|---|---|
| BLOCK/INSERT | INSERT/MINSERT are expanded into ordinary copies when a file is read; the editor has no block-reference entity. INSERT from the library also places copies. Block structure, attributes and dynamic-block parameters are lost on save. | `dxf-reader.ts` case "INSERT"; header of `cad-blocks.ts` ("no block-reference entity") |
| SPLINE / ELLIPSE | Were tessellated to polylines and the true definition discarded. **Fixed in M1** (see §4). | `dxf-reader.ts`, `acad-engine.ts` |
| MLINE | Drawn as its centre path only. | `acad-extra-entities.ts` header |
| TABLE | Grid and cell text only; merged cells and border styles dropped. | same |
| REGION / boundary | Approximated through polylines/hatch loops; no region entity. | model has no REGION type |
| XREF | Attach reads the file and merges its entities onto layers prefixed `XREF_<name>\|`, with a cache for nested reload. No overlay/clip/true reference semantics. `XrefManager` tracks nesting and detach. | `cad-viewer.ts` ~3295, `acad-advanced.ts` XrefManager |
| Layouts | Only the active paper space is written; extra layouts are not saved. | `dxf-writer.ts` `layoutsNotSaved` |
| Parametrics | Constraint commands apply one-shot corrections (`fixHorizontal`, `fixParallel`, `fixTangent`, …). No persistent constraint graph / solver observed in the drawing model. | `src/features/cad-params.ts` |
| Sheet sets | Basic SHEETSET command exists (add/rename sheets); no plot-set or publish metadata round trip observed. | `cad-viewer.ts` ~9897 |
| Automation | A small LISP subset (`command`, `setq`, `defun`, `princ`) exists in `cad-viewer.ts`; no documented sandbox, plugin interface or transaction API. | `cad-viewer.ts` ~9924 |
| Interop corpus | 10 DXF files generated by ezdxf with an independent-validation test; 3 DWG samples. No desktop-CAD validation. | `tests/fixtures/dxf-corpus`, `tests/dxf-independent-validation.test.cjs` |

Rows marked "observed" were located by search and not exhaustively exercised; treat them as Limited until a
milestone proves otherwise.

## 4. M1 — what shipped and its limits

- `src/modules/drawings/native-curves.ts` stores the true SPLINE (degree, control points, knots, weights, fit points,
  closed) or ELLIPSE (centre, major axis, ratio, start/end parameter) next to the tessellated polyline.
- A signature of the tessellated points guards every use. If a command changes the points without carrying the
  definition along, the definition is treated as stale and the entity is saved as the current polyline. Stale data
  can never overwrite an edit.
- Move, rotate, uniform scale and mirror carry the definition exactly (`modify-math.ts`).
- The DXF writer emits real `SPLINE` / `ELLIPSE` records (not in the legacy R12 prologue).
- Both DXF and DWG-engine readers attach the definition.
- **Limits**: trim, extend, break, stretch, fillet, offset, array, clipboard paste and the LibreDWG fallback reader
  still produce plain polylines (honest flattening, no stale data). Tessellation ignores spline weights, so rational
  splines display approximately although their weights are preserved in the file. Spline and ellipse editing
  (grip editing of control points) is not part of M1.
- **Tests**: `tests/native-curves.test.cjs` (7 checks: read, write, affine carry, stale guard, malformed input).

## 7. Phase 4 — deterministic constraint solver (core)

`src/modules/cad-viewer/constraint-solver.ts` (pure): unknowns are point coordinates and radii; 16 constraint types
(coincident, horizontal, vertical, parallel, perpendicular, tangent line–circle, tangent circle–circle (external/internal),
concentric, equal length, equal radius, symmetric, fixed, distance, length, radius, angle). Levenberg–Marquardt with
central-difference Jacobians, sorted-id processing (same input → same output; constraint order irrelevant).
Diagnostics: status (`solved` / `underconstrained` / `overconstrained` / `conflict` / `diverged` / `invalid`), remaining
DOF (Jacobian rank), redundant constraint ids, conflicting constraint ids (removal makes the rest converge), residual,
iterations. On conflict the sketch is returned unchanged. Constraint list (de)serialisation is validated.

Verified (`tests/cad-constraint-solver.test.cjs`, 14): every constraint type, DOF counts, redundancy, conflict detection,
determinism, invalid input, a 60-link / 122-variable chain (≈65 ms, 6 iterations).

**Editor integration (Phase 4b).** `constraint-bridge.ts` maps LINE / CIRCLE / ARC entities and recorded relations onto the
solver. The Parametric tab's HORIZONTAL, VERTICAL, PARALLEL, PERPENDICULAR, TANGENT, CONCENTRIC, EQUAL, DCLINEAR, DCRADIUS and
DCDIAMETER now also *record* the relation; `GCSOLVE` (ribbon: Manage › Solve All) re-solves all of them together as one
undoable edit, `GCLIST` (Manage › Constraints) shows each one as ok / redundant / CONFLICT, `GCCLEAR` forgets them. FIX'd
objects stay put (centre and radius). A conflicting or diverged set is refused — geometry is not changed. Verified:
`tests/cad-constraint-bridge.test.cjs` (9) and the browser spec `cad-constraints.spec.ts`.
*Limits:* relations are session-scoped (not written to DXF/DWG), so they are lost on reload; COINCIDENT, SYMMETRIC and
DCANGULAR still apply once without being tracked; relations do not re-solve automatically while dragging; ARC angles and
polylines/splines are not solved; no per-relation delete yet (GCCLEAR clears all).

**Not done (honest):** no editor integration yet (no commands, no on-canvas constraint creation, no persistence into the
DXF file — constraints live only in the model/JSON); arcs are modelled as centre+radius+end points but arc-angle
consistency is not enforced; no ellipse/spline constraints; analytic Jacobians would be faster for very large sketches;
no "drag while solving" API yet; solver not benchmarked beyond the chain above.
## 5. M2a — native block references (data model and DXF path)

**What exists**

- `DxfInsert` entity and `DxfDocument.blocks` (`dxf-types.ts`). References name a definition; geometry is never copied.
- `block-refs.ts`: `resolveInsert` (nested, MINSERT, attributes, constant ATTDEF, layer-0 inheritance), `explodeInsert`
  (one level), `flattenInserts` (for consumers that only understand primitives), `unusedBlocks`, binding and a cache
  (`bindDocumentBlocks`, `resolvedOf`, `touchBlocks`).
- Hard limits: nesting 8, 250 000 resolved entities per call, MINSERT axes clamped to 500, cycles reported. Hostile
  files cannot hang or exhaust memory.
- Support in `entityBBox`, `distToEntity`, snap points (new `insertion` snap), `entitySignature`, spatial index,
  translate / rotate / scale / mirror / stretch, OCS flip.
- DXF reader (`parseDxf(text, { nativeBlocks: true })`) and writer (BLOCK_RECORD table, BLOCKS section, INSERT +
  ATTRIB + SEQEND, ATTDEF). Reading with the default options is unchanged (flat copies, no `blocks`).
- Because adding `INSERT` to the entity union makes TypeScript list every switch that must handle it, the compiler
  checked the ten exhaustive switches in the CAD code; each now has an INSERT case.

**Evidence**

- `tests/cad-block-refs.test.cjs`: 21 checks, including equivalence with the legacy expanding reader across
  rotation, non-uniform scale, mirror, nesting and MINSERT; cycles, depth and MINSERT bombs; hostile values; three
  write/read cycles stable.
- `bench/block-refs-bench.cjs` (20 000 references × 60 entities = 1.2 M primitives): read 584 ms / ~6 MB native vs
  1122 ms / ~255 MB copied; write 30 ms vs 6005 ms.

**Limits (not hidden)**

- (Superseded by §6: the editor now renders and edits native references; opening files natively is opt-in.)
- The LibreDWG fallback reader still expands blocks.
- A nested reference under a non-uniform parent scale with a rotated child is approximated (the composite is not a
  rotation × scale).
- BYBLOCK colour/linetype are not modelled (inherited as BYLAYER, as before).
- Dynamic-block parameters/actions are not interpreted; anonymous `*U` definitions are stored and resolve as ordinary
  blocks.
- `transformEntity` flattens spline/ellipse definitions inside block bodies to their tessellation.
- Not validated against a desktop CAD application. An independent ezdxf check of written files runs in CI only.

## 6. M2b — editor-native blocks (Phase 1)

**Implemented (unit/integration-tested; browser test written, see Evidence)**

- `block-edit.ts` (pure): `createBlock` (name validation, redefine, base shift, cycle rejection), `makeInsert`
  (scale, rotation, MINSERT, ATTDEF default/override values), `explodeInDoc`, `atteditInsert`, `wblockDocument`
  (nested definitions + layers travel with it), `purgeBlocks`, `blockClosure`/`wouldCycle`.
- Editor: INSERT is drawn by resolving the definition lazily (layer visibility, colours, linetypes from the children;
  highlight and ghost overlays keep their own style). BLOCK now creates a native definition and, by default, replaces
  the selection with one reference; INSERT places a native reference (scale, rotation, MINSERT, attribute prompts)
  and materialises library blocks as native definitions; EXPLODE turns a reference into its one-level children;
  ATTEDIT edits a reference's attribute values; WBLOCK writes references with their nested definitions; SVG export
  resolves references.
- Undo/redo: entity change and block-table snapshot are one transaction (`blocksBefore/blocksAfter`).
- Copied / moved / pasted references (new objects) resolve through the active drawing's block table
  (`setActiveBlocks`), so they never silently vanish.
- The DWG/DXF engine reader has a native mode (`parseWithAcadEngine(bytes, name, { nativeBlocks })`, threaded through
  the reader worker and `readCadFile`): INSERT with scale/rotation/MINSERT (no 64-cell clamp), ATTRIB values, ATTDEF
  definitions, nested references, one definition table. Verified against the real wasm engine on a DXF and on
  `sample_2000.dwg` / `sample_2018.dwg` (line/circle/arc counts equal the legacy expanded result).
- Selection, bbox, spatial index, snap (`insertion` snap) and grips use the reference's bounding box and insertion
  point (M2a).

**Limits (not hidden)**

- Opening files with native blocks is **opt-in** (`NATIVEBLOCKS ON`, applies to the next file) and **experimental**:
  about thirty modules still read `doc.entities` expecting primitives (plot/PDF, queries, IFC bridge, …) and have
  not been audited for INSERT. Only DXF/DWG save, SVG export and WBLOCK are known to handle it. It becomes the default
  only after that audit and a green browser run.
- No block-instance in-place editing (BEDIT) yet: a definition changes only through BLOCK with the same name
  (redefine, all references update). No attribute-definition authoring command (ATTDEF); ATTDEFs come from files.
- Block editing uses a whole-table snapshot (shallow) for undo: fine for hundreds of definitions, not designed for
  tens of thousands.
- BYBLOCK colour/linetype are still not inherited from the reference; dynamic blocks are not interpreted; nested
  references under non-uniform scale with rotated children are approximated; LibreDWG fallback still expands.
- Grips for a reference move its insertion point only (no per-attribute grips).
- Browser evidence: `tests/e2e/cad-native-blocks.spec.ts` (import → SELECTALL → BLOCK → EXPLODE → UNDO ×2 → REDO, with
  a zero-page-error assertion) runs green in the standalone `cad-e2e` workflow (Chromium). Its first run found a real
  bug (UNDO/REDO kept stale selection indices after an N→M replace → crash in showProps); fixed by clearing the selection.
  Not browser-tested: INSERT with attributes/MINSERT dialogs, ATTEDIT, WBLOCK, `NATIVEBLOCKS ON` file open.

**Benchmark (20 000 references × 60 entities, Node, this sandbox, single run — not p50/p95)**

read native 732 ms (~215 MB heap) vs legacy copies 1111 ms (~283 MB); first bbox pass 546 ms, cached 119 ms; index
build 131 ms; 200 snap queries 13 ms; write native 38 ms vs 7454 ms. The p50/p95 harness is Phase 5.
