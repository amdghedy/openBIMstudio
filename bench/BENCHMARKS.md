# OpenBIMStudio — Performance Engineering Milestone

Reproducible, measurement-driven performance pass. **Every number in this
report is produced by a script in `bench/` against the real production
pipelines** — nothing is estimated or copied from another project.

Three measurement generations (all reproducible from `bench/results/*.json`):

| label | build | meaning |
|---|---|---|
| `baseline` | pre-optimization | original app, before any perf work |
| `after` | plan/hover/render-lifecycle pass | first optimization pass |
| `pause-queue` | + import-queue render pause | this pass (see §7) |

## How to reproduce

```bash
npm install && npm run build          # build the app (dist/)
npm run bench:fixtures                # regenerate deterministic IFC fixtures (bench/fixtures/)
npm run bench:node                    # Node-level benchmarks → bench/results/node-<label>.json
npm run bench:browser                 # browser benchmarks → bench/results/browser-<label>.json
npm run bench:budget                  # enforce scripts/budget.json against the latest results
npm run bench:compare                 # before/after table from bench/results/*.json
node bench/probe-fed.mjs              # federation import decomposition (renderer live vs paused)
node bench/probe-reload.mjs           # reload lifecycle leak check (double reload + idle)
```

The browser harness drives the built app through the real UI/production
entry points: real `importFiles()` → web-ifc → fragments → scene, real
`OBC.Raycasters` picks, real properties palette open, real plan-view
pointer events, and real reloads for memory lifecycle. Chromium headless
with `--use-gl=swiftshader` (software GL), 1600×900, `--enable-precise-memory-info`,
`--js-flags=--expose-gc`.

**Measurement caveat (read before comparing):** under software GL every
frame is CPU-rasterized, so *fill-bound* numbers (frame cadence, pick
latency on loaded models) are upper bounds and vary run-to-run.
*CPU-bound* numbers (parse, serialization, spatial index, 2D pointer
processing with the 3D loop paused) are representative. No GPU-bound
number in this report should be read as a promise about real hardware.

## What was measured — and what it proved

### 1. IFC parsing is NOT the bottleneck
`web-ifc 0.0.77` parses the large fixture (2036 elements, 2.4 MB) in
~210 ms in isolation. The real import cost splits (production
instrumentation, `__obsPerf.importPhases()`):

| fixture | conversion (web-ifc→FRAG, worker) | fragments scene load (main thread) |
|---|---|---|
| small | 827 ms | 668 ms |
| medium | 1166 ms | 555 ms |
| large | 2507 ms | 692 ms |

Two real costs live in the vendor libraries: single-threaded conversion
(the app forces `forceSingleThread=true` for WASM ABI safety) and a
main-thread fragments load (~2–3 ms per element, blocks the UI thread
for large models). Both are upstream design; re-implementing them is out
of scope and would be a rewrite — documented, not touched.

### 2. The hidden-3D-loop tax on 2D work (fixed)
The Floor Plan overlay covers the 3D viewport, but the 3D renderer kept
rendering the fully hidden scene every frame. Under software GL that
loop monopolized the main thread (~200 ms/frame at large) and inflated
every 2D interaction: pausing it isolated the true plan cost at
**59 fps / 3.8 ms per pointer move**.
**Fix:** `src/core/renderer-lifecycle.ts` — the plan now pauses the OBC
`SimpleRenderer` while open and resumes on close
(`plan-view-panel.ts setPlanRenderer3d`). Measured end-to-end:
pan 9→57 fps, 30-move burst 3213→113 ms.

### 3. Hover picking during camera drags (fixed)
`selection.ts` fired a hover pick on *every* `pointermove` — including
drags. Each pick is a full GPU ID-render pass (`FastModelPickers`).
**Fix:** `src/core/hover-gate.ts` — picks are suppressed while any pointer
button is held; the stale preselect highlight clears once at drag start.
Production counter (`__obsPerf.countHoverPicks()`): **60 held moves → 0
picks**; free moves still pick (deduplicated by the existing
`hoverPending` guard).

### 4. Full SVG rebuild per pointermove in the plan (fixed)
`renderPlan()` clears `svg.innerHTML` and rebuilds every child — the pan
and drag handlers called it once per pointermove event (~60–120 Hz),
i.e. multiple full rebuilds per displayed frame.
**Fix:** `src/core/raf-coalescer.ts` — one rebuild per animation frame on
the five pointer-driven hot paths (pan, dim/annotation/region/element
drags). One-shot edits still render synchronously.

### 5. Memory lifecycle (verified, no leak)
First import allocates ~270 MB on top of the 40 MB boot heap.
**CDP `HeapProfiler.startSampling` during the import shows <1.5 MB of JS
allocations** — the delta is WebAssembly linear memory (web-ifc worker +
fragments core), a one-time reservation, not per-model bloat: re-importing
the same fixture adds ~38 MB. After a full reload the heap returns to
58 MB — **everything is reclaimable; no leak**. `disposeModel` paths and
the aux-object disposal in `file-interop.ts` were audited and left intact.

### 6. Things we deliberately did NOT change (measured, documented)
- **BVH on fragment meshes is ineffective** — the existing
  `performance-engine.ts` BVH patch builds boundsTrees, but fragment
  picking rides the GPU fast-pick and `world.meshes` is empty, so scene
  raycasts never traverse those meshes. Measured: raycast with BVH
  915→1027 ms (large, noise) — no win, no regression; the patch stays
  because it *does* accelerate authored/aux mesh picking.
- **InstancedMesh batching** stays OFF (opt-in) — fragment geometry is
  already instanced by the fragments library (17 draw calls / 30k tris
  for the large fixture — a healthy render profile).
- **Import queue pipelining** — the queue stays serial; the *render-loop
  contention* that inflated it was fixed in §7 instead (a bounded,
  measured change). Pipelining convert(N+1) with load(N) could still save
  ~1.2 s of the remaining ~2.3 s probe wall, but requires restructuring
  queue cancellation semantics — poor ROI, documented as future work.
- **Properties palette open** (152–782 ms under software GL) scales with
  frame queueing, not with its own logic — the pure snapshot is 7 ms at
  5000 elements. No change.

### First-pass regression safety

- New unit tests: `tests/perf-harness.test.cjs` (10 assertions) —

## 7. Import-queue render pause (this pass)

### 7.1 The measured bottleneck

The first pass left one measured bottleneck documented but unclaimed: the
serial IFC import queue. `bench/probe-fed.mjs` decomposes a 4-file
federation import (fed-a..d, 247 elements each) **in the real bench context
— small + medium + large already in the scene** and attributes every
millisecond via the production phase log:

| arm | wall (import → 4 models registered) | Σ convert | Σ fragLoad | per-file convert |
|---|---|---|---|---|
| renderer live (pre-fix production behavior) | **16862 ms** | 6880 ms | 3583 ms | 1553–1805 ms |
| renderer paused (diagnostic ceiling) | **2410 ms** | 1572 ms | 1231 ms | 302–581 ms |

The gap is main-thread contention: with the 3D loop live, every
software-GL frame (~200 ms/frame at this scene weight) starved the
web-ifc progress handling and the fragments chunk parsing. On a *clean*
page (no models loaded) the same fed files import in ~8.9 s — the
inflation grows with scene weight, i.e. exactly the "large federated
models" case. Queue-UI fixed overhead was measured at **267 ms of the
16862 ms** — negligible; the queue itself is not the cost.

### 7.2 The fix (mechanism already proven by the plan overlay)

`src/features/importer.ts`: `processQueue()` and `loadFragFiles()` now
pause the 3D render loop while the queue mutates the scene and restore it
in `finally` — *before* positioning/autofit so the final camera state
renders. The pause is a captured guard, `pauseRenderLoop()` in
`src/core/renderer-lifecycle.ts`: if the plan overlay already paused the
loop, the import's restore is a no-op and vice versa — the two pause
sources compose instead of fighting (6 new unit tests in
`tests/perf-harness.test.cjs`, 16 total).

### 7.3 After — reproducible numbers

`node bench/probe-fed.mjs` (production path, renderer pause now built in):

| run | wall | Σ convert | Σ fragLoad | renderer after settle |
|---|---|---|---|---|
| run 1 | 2081 ms | 1511 ms | 377 ms | enabled ✓ |
| run 2 | 2268 ms | 1572 ms | 369 ms | enabled ✓ |

Full bench suite (`npm run bench:browser`, results in
`browser-pause-queue.json`), three generations side by side — medians,
software-GL harness:

| benchmark | baseline | after (pass 1) | pause-queue (this pass) |
|---|---|---|---|
| **federated 4-file load** | 16966 ms | 26220 ms (noise band 17–28 s) | **4544 ms** |
| large load (2036 el) | 4940 ms | 5882 ms | **2758 ms** |
| medium load (382 el) | 2312 ms | 2875 ms | **1398 ms** |
| small load (46 el) | 2289 ms | 2331 ms | **1403 ms** |
| 2D plan pan fps | 9 fps | 57 fps | 56 fps (no regression) |
| 2D plan burst ×30 | 3213 ms | 112.8 ms | 111.8 ms (no regression) |
| hover picks, 60 held moves | 1/move | 0 | 0 (no regression) |
| boot → canvas+ribbon | 3.42 s | 3.62 s | 3.64 s (noise) |

The federation win in the full bench (4544 ms) is smaller than the
probe's ceiling (2081–2268 ms) because the bench measures wall clock to
*registration* of the 4th model plus its own per-file repeats and settle
windows; both numbers are honest and reproducible from their scripts.

### 7.4 Memory lifecycle re-verified (no leak)

`bench/probe-reload.mjs` — 7-model session (small + medium + large +
fed×4), then two full reloads and an idle settle:

| checkpoint | heap |
|---|---|
| session (7 models, gc) | 181.6 MB |
| reload #1 (+3 s, gc) | 56 MB |
| reload #2 (+3 s, gc) | 57 MB |
| +8 s idle (gc) | 56.3 MB |

Everything is reclaimable; the pause guard adds no retained memory. One
bench run read 190 MB at the first-reload checkpoint — the double-reload
probe shows that reading is transient post-boot settling, not retention
(the same checkpoint measures 56–57 MB when settled).

## Budget gate semantics (fail-closed)
`node bench/check-budgets.mjs [--require bundle,import,node]` — default requires `bundle`. A required check whose input is missing, malformed, or non-finite **fails** (non-zero exit); non-required missing inputs print `SKIPPED <check>` on stderr. Import/node checks need `bench/results/{browser,node}-after.json` produced by `bench-browser.mjs` / `bench-node.mjs`; CI does not yet produce them, so only the bundle budget is a blocking release gate today. Tested by `tests/perf-budget-gate.test.cjs`.

## 9. Scale target — 20,398-element IFC (`xlarge`), UNMEASURED

### 9.1 The target

One scale target, chosen 2026-11-21 (hardening item 22). The binding
number is the **element count**, not the file size: file size follows
the fixture density (~1.2 KB/element), and a real-world 100 MB model
would be ~80,000 elements at that density — this target does not claim
that. It closes ~one order of magnitude of the ~100× gap between what
was tested (2,036 elements) and real project scale; it does not close
the gap.

| | |
|---|---|
| Fixture | `bench/fixtures/xlarge.ifc` (generated on demand, **not checked in**) |
| Generator | `bench/gen-fixtures.mjs`, tier `xlarge`: 18 floors, 16×12 room grid |
| Elements | **20,398** (10.0× the `large` tier's 2,036) |
| Bytes | **25,396,235** (~24.2 MiB; 10.3× the `large` tier) |
| Storeys / openings | 18 / 2,376 |
| By class | IFCWALL 7,416; IFCSLAB 3,456; IFCWINDOW 504; IFCDOOR 1,872; IFCCOLUMN 3,910; IFCBEAM 3,240 (plus one row each of IFCWALLTYPE / IFCSLABTYPE / IFCCOLUMNTYPE / IFCBEAMTYPE, added by #256) |
| SHA-256 | `038db43bf4f4208e409749ceeb82887861c2a852dd13fc729425b61338fefae8` |
| Determinism | Verified 2026-11-21: two consecutive generations on `bb0f55c` are byte-identical (same SHA-256). The SHA is a canary for the exporter: if a later regeneration gives a different hash, the exporter changed — record the new hash and the exporter change deliberately, do not silently proceed. (Note: the fixtures checked in on `bb0f55c` predate #256; regenerating them adds 8 lines per file from the IfcXxxType rows. That re-cut is out of scope here; the recorded `xlarge` SHA is for the `bb0f55c` exporter.) |

Why the file is not checked in: it is reproducible byte-for-byte from
checked-in code (`npm run bench:fixtures`), and a 24 MB blob would tax
every clone forever. The generator is the fixture's source of truth;
the SHA above is how a later run proves it generated the same file.
`bench-node.mjs` skips a manifest fixture whose file is absent (with a
warning) instead of crashing, and `bench-browser.mjs` fails with a
usable message when a requested size is not in the manifest — so a
fresh clone's default bench runs are unaffected and the scale-target run
fails loudly until fixtures are generated.

### 9.2 Why this target, and not the 580k-entity DWG

The hardening plan offered two candidates. The DWG was rejected as the
primary target on evidence, not preference:

- The 580k-entity drawing is **not in the repo** (only 5–22 KB DWG
  fixtures) — it is the owner's file, and no copy is available to
  measure against.
- The reader that opened it in the past — the LibreDWG fallback — was
  removed from the shipped build on 2026-11-16 (GPL-3.0;
  `docs/COMMERCIAL-READINESS.md` L1, `CHANGELOG.md`). The built-in
  acadrust engine has never opened that drawing, and the trade-off is
  recorded as "must be re-tested". Measuring the DWG target therefore
  needs the owner's file *plus* either the optional LibreDWG plug-in or
  acadrust support for it — two unblockers outside this item.
- The IFC target is measurable with what exists today: a deterministic
  generator driven by the production writer, and a bench harness that
  already takes `--sizes xlarge` (`bench-browser.mjs`) and iterates the
  manifest (`bench-node.mjs`). No new infrastructure was needed.

The DWG re-test stays open as a separate, future target: it needs the
owner's file and a reader decision, and passing the IFC target says
nothing about it.

### 9.4 Measurement procedure (real hardware only)

**Prerequisites — the machine.** A dedicated GPU (not SwiftShader /
llvmpipe / any software rasterizer), ≥ 4 physical CPU cores, ≥ 16 GB
RAM, Chromium with GPU compositing actually engaged (verify in
`chrome://gpu`: "WebGL: Hardware accelerated"). Record in the results:
GPU model + driver version, CPU model + core count, RAM, OS + version,
Chromium version, viewport (1600×900), and the exact build SHA
measured. Standard GitHub-hosted CI runners have no GPU and do **not**
qualify; a self-hosted GPU runner or a local run is required.

**Procedure — exact commands, from a clean checkout:**

```bash
git clone <repo> && cd <repo> && git checkout <build-SHA>
npm ci --legacy-peer-deps
npm run build
npm run bench:fixtures
# Verify the generated target fixture is the recorded one:
sha256sum bench/fixtures/xlarge.ifc
#   must be 038db43bf4f4208e409749ceeb82887861c2a852dd13fc729425b61338fefae8
#   (on the bb0f55c exporter; see §9.1 if it differs)
npm run bench:browser -- --label scale-target --sizes xlarge --repeats 3
npm run bench:node -- --label scale-target
```

**Metrics to capture** (from `bench/results/browser-scale-target.json`
and `bench/results/node-scale-target.json`): `loadTotalMs`,
`heapAfterMB`, `heapDeltaMB`, `fpsIdle.fps`, `fpsOrbit.fps`,
`raycastMs.median`, `propertiesOpenMs`, `elements` (must equal 20,398
— if the app reports fewer, the import dropped elements and the run is
invalid), plus the node `ifc-parse.xlarge.parseMs.median`. Fill in the
§9.5 table from those files; attach the two JSON files. Do **not** edit
the §9.3 targets to match the result: a miss is recorded as a miss, and
any target revision needs its own justification.

**Gate interaction (item 11).** The perf-budget gate
(`bench/check-budgets.mjs`) must measure the PR first, or these numbers
rot the same way the 14 Nov numbers did: item 11 (branch
`fix/perf-budgets-fail-on-missing`, unmerged at the time of writing)
makes CI measure fresh and fail on missing/stale results. Until item 11
lands, the §9.5 table is the only record and nothing enforces its
freshness; once it lands, the scale-target result files fall under its
freshness rule (≤ 7 days) and a follow-up should wire `xlarge` into the
gate as its own suite instead of overloading the `large` import budget.

### 9.6 What passing this target would — and would not — prove

- It would prove the import + render path holds together at 10× the
  previously tested element count on real hardware, within the stated
  load / heap / fps targets.
- It would **not** prove: 100 MB / ~80,000-element models; DWG scale
  (§9.2); federated multi-file sessions at scale; multi-model memory
  lifecycle; or performance on any other GPU than the one measured.
  Each of those needs its own target and its own run.
