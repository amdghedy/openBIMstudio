# OpenBIMStudio — Performance Engineering Milestone

Reproducible, measurement-driven performance pass. **Every number in this
report is produced by a script in `bench/` against the real production
pipelines** — nothing is estimated or copied from another project.

## How to reproduce

```bash
npm install && npm run build          # build the app (dist/)
npm run bench:fixtures                # regenerate deterministic IFC fixtures (bench/fixtures/)
npm run bench:node                    # Node-level benchmarks → bench/results/node-<label>.json
npm run bench:browser                 # browser benchmarks → bench/results/browser-<label>.json
npm run bench:budget                  # enforce scripts/budget.json against the latest results
npm run bench:compare                 # before/after table from bench/results/*.json
```

The browser harness drives the built app through the real UI/production
entry points: real `importFiles()` → web-ifc → fragments → scene, real
`OBC.Raycasters` picks, real properties palette open, real plan-view
pointer events, and real reloads for memory lifecycle. Chromium headless
with `--use-gl=swiftshader` (software GL), 1600×900, `--enable-precise-memory-info`,
`--js-flags=--expose-gc`.

**Measurement caveat (read before comparing):** under software GL every
frame is CPU-rasterized, so *fill-bound* numbers (frame cadence, pick
latency on loaded models) are upper bounds and vary run-to-run.
*CPU-bound* numbers (parse, serialization, spatial index, 2D pointer
processing with the 3D loop paused) are representative. No GPU-bound
number in this report should be read as a promise about real hardware.

## Baselines → After (all measured, medians)

### Node-level (CPU-bound, representative)

| benchmark | baseline | after |
|---|---|---|
| web-ifc parse + full geometry load, large (2036 el) | 212.3 ms | 205.7 ms |
| IFC writer (serialization), large | 91.9 ms | 87.0 ms |
| snapping octree build, 8000 items | 45.7 ms | 46.3 ms |
| snapping octree, 2000 queries, 8000 items | 39.1 ms | 38.5 ms |
| properties snapshot, 5000 elements | 7.2 ms | 7.4 ms |

Pure-logic paths were already healthy and stay within noise: the IFC
*parse* itself was never the bottleneck.

### Browser-level (software-GL harness)

| benchmark | baseline build | optimized build |
|---|---|---|
| boot → canvas+ribbon | 3.42 s | 3.62 s (noise) |
| 2D plan pan fps (40 walls) | 9 fps (p95 300 ms) | **57 fps (p95 16.7 ms)** |
| 2D plan pointer burst ×30 | **3213 ms** | **113 ms (−28×)** |
| hover GPU picks, 60 held-button moves | 1 pick per move (by code — see below) | **0 picks** (production counter) |
| large load total | 4.9–5.7 s | 5.9 s (noise band) |
| federated 4-file load | 17–28 s | 26 s (noise band) |
| heap after full reload (leak check) | 57 MB | 59 MB (fully reclaimed) |

Load-time and raycast deltas between builds are **inside the
run-to-run noise band** of the software-GL harness (baseline-diag run
measured 28.2 s for federation on the *same* baseline build; runs vary
±50%). The real, reproducible wins are the 2D plan numbers and the hover
pick suppression — both directly caused by the changes below.

## What was measured — and what it proved

### 1. IFC parsing is NOT the bottleneck
`web-ifc 0.0.77` parses the large fixture (2036 elements, 2.4 MB) in
~210 ms in isolation. The real import cost splits (production
instrumentation, `__obsPerf.importPhases()`):

| fixture | conversion (web-ifc→FRAG, worker) | fragments scene load (main thread) |
|---|---|---|
| small | 827 ms | 668 ms |
| medium | 1166 ms | 555 ms |
| large | 2507 ms | 692 ms |

Two real costs live in the vendor libraries: single-threaded conversion
(the app forces `forceSingleThread=true` for WASM ABI safety) and a
main-thread fragments load (~2–3 ms per element, blocks the UI thread
for large models). Both are upstream design; re-implementing them is out
of scope and would be a rewrite — documented, not touched.

### 2. The hidden-3D-loop tax on 2D work (fixed)
The Floor Plan overlay covers the 3D viewport, but the 3D renderer kept
rendering the fully hidden scene every frame. Under software GL that
loop monopolized the main thread (~200 ms/frame at large) and inflated
every 2D interaction: pausing it isolated the true plan cost at
**59 fps / 3.8 ms per pointer move**.
**Fix:** `src/core/renderer-lifecycle.ts` — the plan now pauses the OBC
`SimpleRenderer` while open and resumes on close
(`plan-view-panel.ts setPlanRenderer3d`). Measured end-to-end:
pan 9→57 fps, 30-move burst 3213→113 ms.

### 3. Hover picking during camera drags (fixed)
`selection.ts` fired a hover pick on *every* `pointermove` — including
drags. Each pick is a full GPU ID-render pass (`FastModelPickers`).
**Fix:** `src/core/hover-gate.ts` — picks are suppressed while any pointer
button is held; the stale preselect highlight clears once at drag start.
Production counter (`__obsPerf.countHoverPicks()`): **60 held moves → 0
picks**; free moves still pick (deduplicated by the existing
`hoverPending` guard).

### 4. Full SVG rebuild per pointermove in the plan (fixed)
`renderPlan()` clears `svg.innerHTML` and rebuilds every child — the pan
and drag handlers called it once per pointermove event (~60–120 Hz),
i.e. multiple full rebuilds per displayed frame.
**Fix:** `src/core/raf-coalescer.ts` — one rebuild per animation frame on
the five pointer-driven hot paths (pan, dim/annotation/region/element
drags). One-shot edits still render synchronously.

### 5. Memory lifecycle (verified, no leak)
First import allocates ~270 MB on top of the 40 MB boot heap.
**CDP `HeapProfiler.startSampling` during the import shows <1.5 MB of JS
allocations** — the delta is WebAssembly linear memory (web-ifc worker +
fragments core), a one-time reservation, not per-model bloat: re-importing
the same fixture adds ~38 MB. After a full reload the heap returns to
58 MB — **everything is reclaimable; no leak**. `disposeModel` paths and
the aux-object disposal in `file-interop.ts` were audited and left intact.

### 6. Things we deliberately did NOT change (measured, documented)
- **BVH on fragment meshes is ineffective** — the existing
  `performance-engine.ts` BVH patch builds boundsTrees, but fragment
  picking rides the GPU fast-pick and `world.meshes` is empty, so scene
  raycasts never traverse those meshes. Measured: raycast with BVH
  915→1027 ms (large, noise) — no win, no regression; the patch stays
  because it *does* accelerate authored/aux mesh picking.
- **InstancedMesh batching** stays OFF (opt-in) — fragment geometry is
  already instanced by the fragments library (17 draw calls / 30k tris
  for the large fixture — a healthy render profile).
- **Import queue is serial** — measured per-file pipeline
  (convert→load) means batch imports sum phases; pipelining could cut a
  4-file federation from ~26 s toward ~10 s but requires restructuring
  the queue. Documented as future work; not attempted (avoid risky
  rewrites).
- **Properties palette open** (152–782 ms under software GL) scales with
  frame queueing, not with its own logic — the pure snapshot is 7 ms at
  5000 elements. No change.

## Regression safety

- New unit tests: `tests/perf-harness.test.cjs` (10 assertions) —
  coalescer semantics (one callback per frame, last-wins, flush,
  late-frame no-op), renderer lifecycle (pause/resume/needsUpdate, no-op
  safety), hover gate (pick suppression, single stale clear).
  Registered as `test:perf-harness` in `package.json` + `ci-unit-tests.mjs`.
- Full CI unit suite: **215/215 passing**.
- E2E (chromium): smoke, orbit-rtl, native-IFC roundtrip
  (import→editable→commit→diff→restore→export), edit-undo-save — all
  passing on the optimized build.
- `scripts/budget.json` is now enforced by `bench/check-budgets.mjs`
  (`npm run bench:budget`): main bundle 723 KB ≤ 2500 KB, large load
  5.9 s ≤ 60 s, heap 189 MB ≤ 1500 MB, node parse 0.21 s ≤ 60 s.
- `__obs` ratchet: unchanged at 727 (diagnostics exposed via
  `ctx.features.importer.lastImportPhases()` and the existing
  `__obsPerf` object — no new window globals).
